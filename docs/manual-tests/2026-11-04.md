## 1. Goal

- Check that every main screen on `main` works end to end with real Google accounts, before production comes back (2026-11-11) and before the address goes to friends.
- Find bugs, UX problems and design problems, on desktop and at phone width (375px).
- Collect the developer's notes on things to change.

## 2. Method

1. **One test per message.** Claude says what to open or click and what should appear.
2. The developer replies:
   - **"תקין"**: passed. Move on.
   - **"דלג"**: skipped. Recorded with the reason, if one was given.
   - **Anything else** is a finding. Claude asks at most one clarifying question, records it, and moves on.
3. Claude updates this file after every test: the result in §5, findings in §6, notes in §7.
4. Severity for findings: **bug** (something is wrong or broken), **UX** (it works but is confusing or awkward), **design** (looks or layout).
5. Claude runs every command (CLAUDE.md §11). The developer never types a command, and `.env` values are never printed or read aloud.

## 7. Developer notes

Things the developer wants changed or looked at, in their own words (translated if needed), whether or not a test turned them up.

- **N1 (2026-11-04, after test 5): notify the recipient.** When a friend shares a recommendation, the other user gets no sign of it. The developer wants some kind of notification or indicator for received recommendations in the future.
  - Context from the code: posts in a community have **no** indicator. A **direct** recommendation (UC-20) does add to the badge on the **Friends** tab, but that hasn't been tried yet (test 13). So this note certainly applies to community posts, and maybe to direct ones too, depending on what test 13 shows.
- **N2 (after test 9): notify the author when they're rated.** When B rates and reviews A's recommendation, A should get a notification. (Today it's only a log line, the "notification stub" from rate-post.md §4.2, which is the hook where a real channel plugs in.)
- **N3 (after test 9): discussion threads.** A future discussion on every recommendation: reply to a review, reply to replies, and so on. In a community, the discussion is open to the whole community.
- **N4 (after test 9): onboarding tutorial.** A future tutorial for every new user: an informative, intuitive guide to the basic features of the site and app. Supporting evidence from this session: where to rate (only from My List, after saving) wasn't discoverable. Even Claude's instructions got it wrong.
- **N5 (after test 10): promotion to admin → notify and/or ask for consent.** When a member is made an admin, they should get a notification, and/or be asked to accept. **Decision deferred:** the developer will decide in a separate session and open it as its own feature (Stage 1 spec first). Keep this note until then.
- **N6 (after test 13): rethink the UI/UX of direct recommendations (UC-20).** Everything works, but the developer isn't fully happy with how the use case is designed in the UI. It may be changed and improved later. Worth reading together with N1 (indicator) and N3 (discussion).
- **N7 (after test 16): edit a post.** The ⋯ menu on your own post offers only **Delete post**. The developer suggests also allowing **Edit**, at least the comment, as a possible future feature. Context: editing was deliberately put **out of scope** in posts-feed.md §2 ("Editing a post or its comment"), posts-delete.md and link-only-posts.md, so this needs its own Stage 1 spec. **Remind the developer at wrap-up.**
- **N8 (after test 20): a visible log-out button.** Sign out lives only on the Profile screen. The developer wants it somewhere visible, such as the dashboard's button bar or another prominent place. Design question for its Stage 1: the bottom nav already has 5 tabs at 375px, so a header or menu entry may fit better than a sixth tab.
- **N9 (after test 20): separate "Sign in" from "Sign up" on Welcome.** Today one **Continue with Google** button serves both a returning user and a new one. The developer asks whether they can be separated, and to implement it later. **Feasible, but it reverses a recorded decision.** CLAUDE.md §5 and docs/auth.md say "Sign-up and login are the same button", so it needs a Stage 1 spec and an update to `auth` (both .md and .docx). Options to weigh there:
  - (a) **Copy only:** keep one flow, but make the screen say both ("Sign in or create an account"), and greet a returning user with "Welcome back". This is the cheapest option, with no new failure paths.
  - (b) **Two buttons, same endpoint:** "Sign in" and "Create account", where the backend gets an `intent` and answers a mismatch helpfully ("No account yet. Create one?" / "You already have an account. Signing you in."). This is clearer, but adds error states and tests.
  - Note: with Google there's no password either way, so the split is about clarity, not security.
- **N10 (during the deferred checks): upload your own profile picture.** The developer asked whether users can pick a photo from their computer. Today they can't: it's rejected in CLAUDE.md §2/§8. The developer then asked whether it's feasible given **fewer than 100 users**, with every image **compressed into a small round avatar**. Claude's assessment: **yes, and cheap at that scale.** About 100 × a ~20–30 KB 256×256 WebP is roughly 3 MB in total.
  - Recommended storage: **the bytes in Postgres** (a small `user_avatars` table or a `bytea` column), served from `GET /api/users/:id/avatar` with cache headers. This adds no new external service, stays provider-agnostic, and fits Neon Free's quota easily. The alternative, object storage (Vercel Blob, S3 or R2), adds a dependency (§18) and is unnecessary at this size.
  - Processing: crop and resize in the browser (canvas → 256px WebP) for a fast upload, **and** re-encode on the server so a crafted file can't get through and EXIF (location) is stripped. Server-side re-encoding most likely means adding `sharp`, which is a **new dependency** (it needs approval per §11) and adds some size to the Docker image (watch the Vercel storage meters, §16).
  - Guards: a size cap (e.g. 2 MB in, ~50 KB out), JPEG/PNG/WebP only, checked by magic bytes and not the file name, and a rate limit on uploads.
  - It **reverses a recorded decision**, so it needs a Stage 1 spec, plus updates to CLAUDE.md §2/§8 and the `frontend screens` / `tables` docs (.md + .docx). Also decide there: can an admin clear an inappropriate photo?
  - An earlier, related question: linking an X/Twitter account just for its photo was discussed and dropped by the developer (a paid API, a second OAuth provider, links that break).
