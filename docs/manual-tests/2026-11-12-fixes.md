### 1. White rectangle behind the Google button (Welcome)

- **Seen:** on the Welcome screen, the "Sign in with Google" button sits inside a white rectangle that stands out against the dark background. It looks bad.
- **Wanted:** no white rectangle. The area around the button should be the same colour as the rest of the screen.
- **Note for the fix session:** the button is rendered by Google inside an iframe (`@react-oauth/google`). A white box around it usually comes from the iframe's `color-scheme` not matching the page's dark scheme, so the browser paints the iframe's default light background. Check that first, before restyling the button itself.

### 2. Em dashes in user-facing copy (all screens)

- **Seen:** user-facing text uses the long dash (—) a lot. It reads like AI-written copy. Example, the tip on My List: "Listened? Rate it here — your score shows on the post."
- **Wanted:** find every place the user sees a string with an em dash and rewrite it so it needs no dash: a full stop, a comma, a colon, or a different sentence.
- **Scope:** only text the user sees: UI copy, toasts, empty states, aria labels, the PWA manifest and `index.html`, and the backend's error `message`s, which the frontend shows as toasts. Code comments and docs are not part of this. The dash is also used as a placeholder for a missing value (for example "—" in an empty table cell); decide in the fix session whether that stays.
- **Size, rough count on 2026-11-12:** about 126 lines in 81 non-test files under `frontend/` contain an em dash, most of them comments. The backend has a few in error messages. The fix session starts by listing the user-facing ones.
- **Tests:** component and integration tests that assert on the old strings must be updated with the copy.

### 3. The "Generated" avatar option (Complete Your Profile)

- **Seen:** under "Your avatar", the selected "Generated" option is a large cream/white card with a pale mint circle inside it. Pale on cream has almost no contrast, and the white block clashes with the dark screen. It looks bad and is wrong as design.
- **Wanted:** another way to show the two options and which one is selected, one that fits the dark design.
- **Notes for the fix session:** the selected state is shown by filling the whole card with the light colour, so whatever avatar is inside loses contrast, and the generated avatar is the lightest one. Options to weigh: mark the selection with a border or ring plus a check instead of a fill, and check the generated avatar against the dark background as well. The same choice appears again on My Profile (choosing or re-choosing the photo), so check that both screens look alike.

### 4. Invite-friends rows link to profiles (Create Community)

- **Seen:** on Create Community, the "Invite friends" list shows each friend with a checkbox. Tapping the friend's name by mistake opens their profile and leaves the form.
- **Wanted:** the friend's name is not a link to their profile on this screen.
- **Notes for the fix session:** the natural behaviour is for a tap anywhere on the row (avatar or name) to toggle the checkbox, which also gives a large touch target. Losing a half-filled form on a mis-tap is the real harm, so check whether the same friend row (with a profile link) is reused elsewhere inside a form, for example inviting friends from Community Settings, and fix it there too.

### 5. Empty screens while moving between pages (all screens)

- **Seen:** on every page change there's a short moment of an empty page structure or empty components (skeletons). Sometimes loading takes several seconds.
- **Asked:** why does it happen, and can a cache fix it?
- **Cause, from reading the code on 2026-11-12:**
  1. **No client-side data cache.** Screens load through `useRequest` (`frontend/src/hooks/useRequest.ts`), which fetches on mount and keeps the result only in the component's state. Leaving a screen throws the data away, so coming back (for example Home → Community → Home) starts from "loading" again and shows the skeleton until the server answers, even for data seen a second ago. This is the short flash on every navigation.
  2. **Cold starts in production.** The backend container on Vercel Hobby scales to zero after 5 minutes idle (docs/deployment.md), and Neon Free also suspends its compute when idle. The first request after a quiet period waits for both to wake up. This is the multi-second wait, and a client cache can't remove it on a first visit.
- **Direction for the fix session:** a client-side cache with stale-while-revalidate: show the last data at once, refresh in the background, and update in place. Options: adopt TanStack Query (a new dependency, so it needs the developer's go and a `docs/tech stack.md` entry, §18), or extend `useRequest` with a small in-memory cache keyed by request. Either way, decide which writes invalidate which lists (post, rate, bookmark, join, and so on), so a screen never shows stale data after the user's own action. For cold starts: measure first (how often, how long), then weigh options. A keep-warm ping costs CPU-hours and would count against the Hobby allowance.
- **Example from the developer:** opening Home ("Your communities") after about 10 minutes away shows empty skeleton cards for 4–5 seconds. 10 minutes is past the 5-minute scale-to-zero, so this is a cold start.
- **Ways to prevent or shorten the cold-start wait, discussed on 2026-11-12:**
  1. **Persist the last data on the device (recommended, biggest visible win).** Keep the last answer for each list (communities, feed, My List, notifications) in `localStorage`/IndexedDB and render it at once on the next visit, then refresh in the background. The server still takes 4–5 s to wake, but the user sees their communities right away instead of skeletons. This is the same cache as the "Direction" above, persisted across visits. Watch: clear it on sign-out (shared devices), and never persist anything sensitive.
  2. **Make the cold start itself shorter: measure first.** Find where the 4–5 s go: container boot, `prisma migrate deploy` running on every start (the image runs migrations on start), Prisma connecting, and Neon's compute waking up. If migrate-on-start is a large share, consider running migrations once per deployment instead of on every container start. That's a deployment change, so it needs a decision in docs/deployment.md.
  3. **A clearer wait.** If a request takes longer than about 2 s, add a quiet line under the skeleton ("Waking up the server…") so the wait reads as expected, not broken.
  4. **Keep the server warm with a scheduled ping: not recommended.** Hobby allows 360 GB-hours of provisioned memory a month, and a container kept up around the clock at 2 GB uses about 1,440. That would exceed the allowance and pause the team for 30 days, as the storage overage did on 2026-10-12. Neon's free compute hours would also run down.
- **Related:** CLAUDE.md §16 requires a service worker that runtime-caches the feed, but a quick look found no `vite-plugin-pwa` runtime-caching rules in `frontend/vite.config.ts`. Check in the fix session where, or whether, the service worker is configured.

### 6. A real guide for new users (onboarding tutorial)

- **Seen:** the walkthrough a new user gets isn't really a guide. It shows sentences that describe the site.
- **Wanted:** a fuller, more informative guide that shows the user pictures of the screens and how to do things (for example: create or join a community, post a link, rate, save to My List, recommend to a friend).
- **Notes for the fix session:**
  - This reworks an existing feature (docs/features/onboarding-tutorial.md, UC-1 / UC-13), so it needs a Stage 1 spec session that amends that spec, not just a code change.
  - Decide the form: illustrated slides with screenshots or mock-ups of each screen, a step-by-step coach-mark tour over the real UI (highlight the button, "tap here"), or a mix (slides first, then tips in place, like the existing save and rating tips).
  - Decide the content: which actions are covered and in what order. Keep it short enough that people finish it, with Skip and a way to reopen it later (for example from My Profile).
  - Images: real screenshots go stale with every UI change. Weigh drawing simplified screens in code (they stay in sync with the design system) against static images (they need re-capturing after redesigns and add weight to the PWA precache).
  - The existing flags (`walkthrough_seen_at`, `save_tip_seen_at`, `list_tip_seen_at`) and whether people who already saw the old walkthrough get the new one.
