## 1. Goal

A user who has just signed in for the first time chooses a display name, a preferred streaming service, and whether their avatar is their Google photo or a generated one. Until they do, the home screen is unreachable. After they do, they land on home, and every later sign-in goes straight there.

## 2. Scope

**In scope**

- The real Complete Your Profile screen, replacing the placeholder from `google-auth.md`.
- `GET /api/users/display-name-availability` (live check while typing) and `PATCH /api/users/me` (save).
- Display-name validation, normalisation, uniqueness key, and the reserved-name list.
- The avatar choice: Google photo or generated, generated by default.
- Schema: `use_google_picture` column; sign-in stops storing the Google photo for users who declined it.
- Doc updates: `tables`, `auth`, `use cases`, `frontend screens` (`.md` + `.docx`), CLAUDE.md §5/§8, `DEVELOPMENT.md`; tick "Merged" on `google-auth.md`.

**Out of scope**

- Editing the profile later (My Profile / Settings, UC-3). `PATCH /api/users/me` is designed so that screen can reuse it, but no settings UI ships here.
- Editing the reserved-name list from the admin area (UC-19). It is a constant in code for now.
- Cross-script look-alikes (Latin "a" vs Cyrillic "а"). Normalisation handles case, accents/niqqud and compatibility forms; full homoglyph detection is not attempted.
- Script-aware mark stripping. The key removes every combining mark, which is the intent for Hebrew niqqud and Latin accents but also merges names in scripts whose vowel signs are marks (Devanagari, Thai). Accepted for this audience; revisit if it bites.
- Re-choosing the Google photo later. A declined photo is not stored, so the future settings screen cannot offer it until a fresh sign-in stores it again — that design belongs to UC-3's spec.
- Rename limits or rename history.
- The real dashboard — `/home` stays a placeholder until Phase 2.

## 3. Data model changes

Migration: `npx prisma migrate dev --name add_use_google_picture`

```prisma
model User {
  // …existing columns…
  /// The user chose their Google photo as their avatar. False until they do.
  useGooglePicture Boolean @default(false) @map("use_google_picture")
}
```

**Photo lifecycle** (changes `auth.service.ts` from `google-auth.md`):

| User state                              | On sign-in                               | On saving the profile                                      |
| --------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| Not onboarded yet                       | Store / refresh `profile_picture_url`    | —                                                          |
| Onboarded, `use_google_picture = true`  | Refresh `profile_picture_url`            | —                                                          |
| Onboarded, `use_google_picture = false` | **Store nothing**; the column stays null | —                                                          |
| Saves with "generated avatar"           | —                                        | `profile_picture_url = null`, `use_google_picture = false` |
| Saves with "Google photo"               | —                                        | `use_google_picture = true`, URL kept                      |

The URL is held before onboarding only so the screen can offer it as a choice.

## 4. Display-name rules

Applied by the server (authoritative) and mirrored on the client for instant feedback.

1. **Clean:** Unicode NFC; typographic apostrophes (`’ ‘ ʼ`) become `'` and Unicode hyphens (`‐ ‑`) become `-` (iOS smart punctuation inserts them while typing); trim; collapse runs of whitespace to one space.
2. **Length:** 2–20 _visible_ characters, counted as grapheme clusters (`Intl.Segmenter`), so "🎧" or a letter with niqqud counts as one. Additionally at most 50 code points, so the `VarChar(50)` columns always fit (only reachable with long emoji sequences).
3. **Allowed characters:** letters in any script, combining marks, digits, spaces, emoji (including skin tones, ZWJ sequences and variation selectors), and `. - _ '`. Anything else is rejected — symbols like `<>@#/`, and invisible characters (zero-width space, bidi marks, control characters, and the Hangul fillers `U+115F U+1160 U+3164 U+FFA0`, which are classified as letters but render blank).
4. **Uniqueness key** (`display_name_key`): NFKD → remove combining marks (accents, niqqud) → remove ZWJ / variation selectors → lower-case → collapse whitespace → trim → NFC. "עֹפְרִי" ≡ "עופרי", "José" ≡ "jose", "Ｏｆｒｉ" ≡ "ofri".
5. **Reserved names:** rejected when the key **equals** a reserved key, or **contains** `bookrough` / `בוקראף`. The list (stored as written, compared by key):
   - App and staff: BookRough, Book Rough, Admin, Administrator, Root, Superuser, Sysadmin, Owner, Staff, Team, Support, Help, Helpdesk, System, Moderator, Mod, Official, Verified, Security, Privacy, Legal, Abuse, Noreply, Info, Contact, API
   - Hebrew: מנהל, מנהלת, הנהלה, אדמין, תמיכה, מערכת, צוות, רשמי, מאומת, בוקראף
   - External services: Spotify, Apple Music, YouTube, Tidal, Deezer, Google, Squigly
   - Confusing / UI-breaking: Bot, Robot, Deleted user, Unknown, Anonymous, Guest, User, Everyone, Here, Me, You, Test, Null, Undefined, משתמש מחוק, אנונימי, אורח, בוט

The rules live in one backend module (`services/displayName.ts`) and one frontend module (`lib/displayName.ts`). The two packages share no code (not a workspace), so the frontend copy is a deliberate mirror; both are unit-tested against the same example table.

## 5. API

### `GET /api/users/display-name-availability?name=<raw>`

- **Auth:** required
- **Request:** query `name`, string, max 200 chars before cleaning.
- **Success:** `200` `{ available: boolean, reason: null | "taken" | "reserved" }`. The caller's own current name counts as available (for the later settings screen).
- **Errors:** `422` name fails rules 1–3 (message names the rule: "Use 2–20 characters." / "That character isn't allowed."); `401` not signed in.

### `PATCH /api/users/me`

- **Auth:** required
- **Request:** `{ displayName?: string, preferredService?: StreamingService, useGooglePicture?: boolean }`, Zod `.strict()`, at least one key. While the user still needs onboarding, `displayName` **and** `preferredService` are required.
- **Behaviour:** validate and normalise the name; check reserved; write `display_name`, `display_name_key`, `preferred_service`; apply the photo lifecycle (§3). `useGooglePicture: true` is rejected when there is no Google photo to use.
- **Success:** `200` `{ user: PublicUser, needsOnboarding: boolean }` — the same session shape as `/auth/me`, so the store is updated in one call.
- **Errors:**
  - `400` body is not JSON.
  - `422` empty body; unknown key; invalid name (rules 1–3); unknown service; missing name or service during onboarding; `useGooglePicture: true` without a Google photo. Reserved name → `422` "That name is reserved."
  - `409` "That display name is already taken." — key collision, including a race between the availability check and the save (Prisma `P2002` → `AppError`).
  - `401` not signed in.

## 6. Screens & components

### Complete Your Profile (`pages/CompleteProfile.tsx`), phone layout first

Top to bottom: heading "Complete your profile"; avatar choice; display name; streaming service; **Continue**; a quiet **Sign out** link.

- **Avatar choice:** two tiles side by side — _Generated_ (initials of the name being typed, colour from the user id, updates live) and _Google photo_. Generated is selected by default. The Google tile is shown only when a Google photo exists. A line under them: "Your Google photo is only kept if you choose it."
- **Display name:** text input, `maxLength` generous, character counter `n/20`. Under it, one status line:
  - typing / too short / invalid character → the rule's message, from the client mirror, no request sent;
  - checking (debounced 400 ms) → small spinner "Checking…";
  - available → "✓ Available";
  - taken → "That display name is already taken."; reserved → "That name is reserved.";
  - check failed (network) → "Couldn't check right now — we'll check when you continue." (does not block submit).
- **Streaming service:** five large radio buttons (Spotify, Apple Music, YouTube, Tidal, Deezer), each ≥ 44 px tall, **none selected**. Label: "Where do you listen?"
- **Continue:** disabled until the name is valid and not known-taken/reserved and a service is chosen. While saving: busy "Saving…". On `409`: the name status switches to "taken" and the button returns. On success: the store is updated and the guard moves to `/home`.
- **Loading state:** the session is already resolved by `SessionGate`; the screen renders immediately.
- **Error state:** any other failure → the global toast (interceptor) and the button returns; the form keeps its values.
- **Offline:** a banner "You're offline. Connect to finish your profile." and Continue disabled.

Home placeholder: unchanged, but now reached through this screen.

## 7. Edge cases & failure modes

- **Two users race for the same name:** both see "Available"; the second save gets `409` and the screen shows "taken". Nothing is half-saved.
- **Abandoned onboarding:** the user closes the app on this screen. Next sign-in: same row, still needs onboarding, back here; the Google photo is still offered.
- **User declines the photo, later changes their Google photo:** sign-in does not store the new URL (the column stays null).
- **No Google photo at all:** only the generated tile shows; `useGooglePicture: true` is rejected server-side.
- **Name that differs only by niqqud/accents/case/full-width from an existing one** → taken.
- **Name made only of spaces or invisible characters** → invalid after cleaning.
- **Very long emoji sequences:** 20 graphemes but > 50 code points → "That name is too long."
- **Unknown service string from a tampered client** → `422`.
- **An onboarded user calls `PATCH /users/me` with only a service** → allowed (settings use case); a user still onboarding doing the same → `422`.
